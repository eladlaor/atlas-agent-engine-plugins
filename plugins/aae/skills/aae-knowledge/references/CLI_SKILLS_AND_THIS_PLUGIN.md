## Summary

- `agentengine init` / `create` writes vendor-maintained skills into each project. They
  are good at three narrow jobs: reading the docs, checking framework code shapes, and
  walking a failed deploy.
- This plugin **complements** them; it does not copy or replace them. When a project has
  them, read the relevant one first, then apply this plugin's knowledge on top.
- What the plugin adds, in order of value: **a dated memory of what the docs don't say**
  (this skill), **utilities the CLI doesn't ship** (add or tear down one agent, docs
  change detection, a prior-art check), and **a subagent rather than only skills** (a
  specialist with its own context and a personal memory overlay).

## Which skills does the agentengine CLI install, and where?

Project-scoped copies, one under `.claude/skills/` (Claude Code) and an identical one under
`.agents/skills/` (Codex and other hosts), in the directory where `init` ran. Observed with
CLI 0.1.118:

| Skill | Does | Observed |
|---|---|---|
| `atlas-agent-engine-docs` | Answers platform questions only from the public docs site, citing the page | 2026-10-04, 2026-10-10 |
| `feature-validations` | Greps agent source for framework shapes the SDK doesn't support (LangGraph, ADK); complements `agentengine validate`, which checks only `agent.yaml` | 2026-10-04, 2026-10-10 |
| `troubleshoot-deploy` | A CLI-only decision tree for stuck or failed deploys, with nine common causes | 2026-10-04, 2026-10-10 |
| `atlas-agent-engine` | Template guide for the scaffolded project | 2026-10-04 in a fresh `init` directory; absent from a monorepo root on 2026-10-10 |

**The misunderstanding to avoid:** they are not global. They load only when the host runs
inside that project directory. Ask an AAE question from anywhere else and none of them is
there.

## Does this plugin replace them?

No. They are maintained by the platform's vendor and regenerated by the CLI, so for the
narrow things they cover they track the platform more closely than any third-party copy
could. The plugin never duplicates their content. `aae-guide` reads the relevant one
first when it is present, and adds what follows.

One caveat worth knowing: as of 2026-10-10 the `atlas-agent-engine-docs` skill still
says the docs site "is not published yet" and tells the model to answer only that the
docs are unavailable. The site has been live since at least 2026-10-04 (HTTP 200 on the
base URL and on `llms.txt`), so in practice the skill works, but a request that fails
for any reason makes it give up rather than fall back. `aae-guide` instead says which
facts it could not verify.

## What does the plugin add that the built-in skills don't have?

**1. Knowledge the docs don't contain (the main value).** The built-in skills can only
know what the docs or the CLI's own decision tree say. This skill records what was
learned by running the platform:

- a dated **drift log** of where the live CLI and platform disagree with the docs;
- **doc contradictions** between pages, and which side turned out right;
- **verified details** the guides bury or omit (OpenAPI-only endpoints, cost accounting,
  memory scoping, identity and role mapping);
- **troubleshooting** for failures outside the deploy path: gateway 404s, misleading
  "API key rejected" errors, egress IP lanes, paused clusters, half-finished `init`,
  read-only commands that start a deploy;
- **runbooks** pinned to a CLI version, such as connecting an external client to a
  deployed workspace and recovering after the Atlas cluster pauses.

**2. Utilities the CLI doesn't ship.**

| Plugin piece | Gap it fills |
|---|---|
| `aae-add-agent` | `agentengine create` scaffolds a whole new project; nothing adds one agent to an existing monorepo |
| `aae-delete-agent` | `workspace delete` alone leaves secrets, sessions and the database user behind |
| `aae-docs-watch` | Nothing tells you the docs changed; this crawls them (nightly, if you schedule it) and reports diffs at session start |
| `aae-scout` | Checks whether the platform, CLI, SDK, official examples or your own repo already do what you're about to build, with a dated verdict |
| `ae` shortcut | A short command name that also works for commands issued by an agent |

**3. A subagent, not only skills.** In Claude Code, `aae-guide` is a subagent: it runs in its
own context window, so a long investigation doesn't flood the main conversation. It also
keeps a **personal memory overlay** (`~/.claude/agent-memory/aae-guide/MEMORY.md`) for the
user's project IDs and their own drift notes, read on top of this baseline.

**4. Available everywhere.** The plugin is installed per user, so it answers from any
directory, including before a project exists.

## Which one should answer a given question?

| Question | Start with | Then |
|---|---|---|
| "What do the docs say about X?" | `atlas-agent-engine-docs` if present, else the docs directly | `DRIFT_LOG.md` and `DOC_CONTRADICTIONS.md`, in case the docs are wrong |
| "Will this graph or ADK shape work?" | `feature-validations` | `SDK_ADAPTERS.md` |
| "My deploy is stuck or failed" | `troubleshoot-deploy` | `TROUBLESHOOTING.md` and `DRIFT_LOG.md`, especially when the deploy succeeded but invoke fails |
| "Does AAE already do X?" | `aae-scout` | `aae-guide` for the design |
| Anything about cost, identity, A2A, CLI targeting, monorepos | this skill's references | the live docs, to re-verify |

## Should the generated skills be committed to the project repo?

Usually not. The CLI owns them and rewrites them on `init`, so a committed copy quietly
goes stale. Add `.claude/skills/` and `.agents/skills/` to the project's `.gitignore`,
unless the project keeps its own hand-written skills there. In that case, ignore the
generated skill directories by name.
